### 시험 중 발견해 고친 결함

1. **승인 표시가 트랜잭션 끝까지 남음** (0400): `approve_proposal`이 켠 'AI 제안 승인' 표시가 같은 트랜잭션의 이후 수동 편집까지 `ai-approved`로 기록할 수 있었다. 할 일을 쓰는 순간에만 켜고 바로 끄도록 바꿨다.
2. **트리거의 비단락 평가** (0500): PL/pgSQL은 `TG_TABLE_NAME = 'project' AND NEW.area_id ...`에서 앞 조건이 거짓이어도 뒤를 읽어, `area` 삽입이 실패했다. 테이블 확인과 열 접근을 중첩 IF로 나눴다.

### TC-08 실제 동시 요청 — REST 경로 (2026-10-18)

**결과: 9/9 통과**
- 같은 새 할 일 제안 20건을 두 세션이 동시에 승인(요청 40개를 한꺼번에, 584ms) → 20쌍 모두 `approved` 1 + `already-approved` 1, 할 일 20건(중복 0), 승인 기록 20건.

- 로그인 없이 공개 키만 → 테이블 읽기·승인 RPC 모두 HTTP 401.

### 보안 점검(Supabase advisor)

- `approve_proposal`·`reject_proposal`을 로그인 사용자가 실행할 수 있다는 경고 2건. **설계 의도대로**다(운영 데이터 변경의 유일한 길이며, 함수 안에서 `auth.uid()`와 소유자를 직접 확인한다. 위 '승인 건너뛰기'·'남의 제안 승인' 시험으로 확인).
- RLS 미적용 테이블 경고 없음.

### 아직 확인하지 않은 것 (TC-01/08 나머지)

- **공개 가입 차단(Google OAuth 연결 후 실기 확인)**: 대시보드 '새 가입 허용'은 끄지 않고(본인 첫 Google 로그인도 막힘, DEC-26) 계정 생성 전 훅으로 막는다. 훅 함수·허용 목록·첫 로그인 준비는 아래 FR-01에서 DB 계층 검증 완료. **실기 연결(2026-10-18)**: Google OAuth 클라이언트(웹, 테스트 중·테스트 사용자 본인만)·Supabase Google 제공자·Before User Created 훅을 켜고 허용 목록에 본인 주소를 넣었다(주소는 DB에만). 첫 시도는 '새 가입 허용'이 꺼져 있어 422로 거부 → 켠 뒤 **본인 Google 로그인 성공, 첫 로그인 준비 트리거로 사용자·설정·'본업' 공간 자동 생성 확인.** 다른 사람은 Google 테스트 사용자 제한과 허용 목록 훅으로 두 겹 차단. 남은 것: 다른 Google 계정으로 시도 시 거부 화면 확인(선택).

### 저장 암호화(M10) — 문서 확인 (2026-10-18)

- Supabase는 고객 데이터를 저장 시 AES-256으로, 전송 중 TLS로 암호화한다([Security at Supabase](https://supabase.com/security)). 디스크와 정기 백업 모두 AES-256이며 키는 FIPS 140-2 HSM으로 보호된다([DPA](https://supabase.com/downloads/docs/Supabase+DPA+250314.pdf)). 키는 프로젝트별로 만들어지고 프로젝트를 지우면 파기된다([데이터 위치 FAQ](https://supabase.com/legal/privacy-resources/data-residency-and-transfers-faq)).
- 공동 책임: 저장 암호화는 Supabase, RLS 등 앱 보안은 우리 몫([Shared Responsibility Model](https://supabase.com/docs/guides/deployment/shared-responsibility-model)). WorkBrain은 RLS(TC-01) + 백업 파일 자체 암호화(DEC-29)로 보완한다. 열 단위 앱 암호화는 P1 범위 밖으로 둔다(필요 시 별도 결정).

## 2. TC-12 백업·복원 — DB 계층 통과, GCS 연결 전 (2026-10-18)

마이그레이션 0600(`wb_backup_export`·`wb_tombstone_export`·`wb_backup_restore`)·0700(부모 없는 행 정리). 시험: `tests/p0/tc12_backup_restore.sql`. **결과: 11/11 통과**

- 백업1 → 할 일 t2 영구 삭제(원장 기록) + t3 삭제 요청(7일 복구 대기) → 백업2·원장 내보내기.
- 백업2에 복구 대기 t3가 빠짐(제외 1건).
- **오래된 백업1을 복원해도 t2가 되살아나지 않음**(원장 1건 적용), **t2의 이력(제목 스냅샷)도 남지 않음**(부모 없는 행 1건 정리), 나머지 할 일·자료 연결은 복원, 운영 테이블은 그대로.
- 삭제 원장이 없거나 백업보다 오래되면 복원 거부. 로그인 사용자·anon은 내보내기·복원 함수 실행 불가(advisor 경고 없음).
- 시험 중 발견해 고친 결함: 원장으로 부모만 지우면 자식 행(지운 할 일의 `task_revision`)에 제목이 남아 되살아남 → 0700에서 외래 키를 따라 연쇄 정리.
- 암호화(`scripts/backup/crypto.mjs`): 왕복 일치, 암호문에 평문 없음, 틀린 암호·변조 파일·12자 미만 암호문 거부 확인.
- **GCS 연결(2026-10-18)**: 사용자가 버킷 `workbrain-backup-26`(서울, 공개 차단, 소프트 삭제 끔, 수명 7일/35일)·넣기 전용 서비스 계정·GitHub 비밀값을 만들었다. 첫 실행은 `gcloud storage cp`가 넣기 전용 권한으로 실패 → JSON API 단순 업로드로 바꿔 **두 번째 실행 성공**(Actions run 39053862150). 파일 이름에 시각을 넣어 같은 날 재실행도 덮어쓰지 않는다.
- **남은 것**: 버킷에서 받은 파일로 `scripts/backup/restore.mjs` 복원 1회(로컬 `.env`에 서비스 키·백업 암호 필요), 실제 데이터가 쌓인 뒤 백업 크기·시간 기록. 한계: 백업 시점 이후에 생긴 '복구 대기' 요청은 그 백업에 반영되지 않는다(복구 대기는 아직 영구 삭제 전이라 원장에 없음).
