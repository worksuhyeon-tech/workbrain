## 2. 검토함 ↔ 보관함 통합

현재 구조(코드 기준):

- 할 일 후보는 `change_proposal(status='pending')`이다. 기록 상세(S05)에서 바로 추가(=승인)하거나 버리고, 검토함(S06)에서 모아 처리한다. 상태·기한 변경 제안(DEC-38)은 검토함에서만 승인한다.
- 미루기(FR-28)는 `snoozed_until` 날짜로 동작한다.
- 아이디어(사용자가 직접 담은 생각)를 넣을 곳이 없다.

통합안(제안):

| 보관함 항목 | 데이터 | 결과 버튼 |
|---|---|---|
| 할 일 후보(회의·녹음) | 기존 `change_proposal` 그대로 | 실행=`approve`, 계속 보관=미루기(날짜 없음 허용), 아카이브=`reject` |
| 변경 제안(DEC-38) | 기존 `change_proposal(target_id 있음)` | 전후 비교 후 승인/거절 — **3버튼에 넣지 않는 것을 권장**. "실행"이 "기존 할 일을 바꾼다"는 뜻이 되어 혼동된다 |
| 아이디어(Quick Capture) | **새 표 필요**(`inbox_item` 가칭: 본문, 추정 맥락, 상태, 만든 시각) | 실행=할 일·프로젝트로 전환(사용자 입력), 계속 보관, 아카이브 |

주의할 점:

1. **AI 제안과 사용자 메모를 같은 표에 넣지 않는다.** `change_proposal`은 분석 실행(`analysis_run_id NOT NULL`)·근거(`evidence_link`)·승인 기록(`approval_event`) 규칙이 붙어 있다. 아이디어는 사용자 본인 입력이라 그 규칙이 필요 없다. 화면에서만 한 목록으로 합친다.
2. "계속 보관"을 FR-28 미루기로 구현하면 미룸 중에도 근거 전사 만료가 진행된다(DEC-15). 오래 보관한 할 일 후보는 6개월 뒤 근거가 사라져 승인이 막힌다(DEC-21). 보관함 화면에 "근거 만료 예정일"을 같이 보여 줘야 한다.
3. 기록 상세에서 바로 추가하는 흐름(DEC-23)은 유지한다. 보관함은 "나중에 몰아서 보는 곳"이다.

## 4. 결함: "처리 중 문제가 생겼어요: No refresh token found in current session"

**확인한 사실(운영 로그, 2026-10-19 KST)**

| 시각 | 기록 |
|---|---|
| 14:53:15 | 같은 초에 토큰 갱신 2건(`token_refreshed` 1 + `token_revoked` 1). 갱신이 동시에 두 번 일어났다 |
| 15:06:50 | `process-record` **401**. 같은 순간 함수가 부른 `/auth/v1/user`가 **`bad_jwt: token is malformed: invalid number of segments`** |
| 15:14:05 | 같은 기록의 처리 완료(REVIEWABLE), 회의록 생성 |
| 15:14:09 | 토큰 갱신 |

어제도 같은 모양이 2번 있었다(10/18 23:37, 10/19 00:06 KST에 401 + bad_jwt).

**해석(2026-10-19 라이브러리 코드로 확인해 고침)**

1. "invalid number of segments"는 함수에 **로그인 토큰이 아닌 공개 키**가 갔다는 뜻이다.
2. supabase-kt 3.1.4의 `currentSessionOrNull()`은 상태가 `Authenticated`일 때만 세션을 준다. 자동 갱신이 인터넷 끊김·서버 오류로 실패하면 상태가 `RefreshFailure`가 되는데, 이때 **세션은 저장소에 그대로 남아 있지만** 메모리 세션은 null이 되어 요청에 공개 키가 붙는다. 라이브러리는 잠시 뒤 스스로 다시 갱신한다.
3. 앱은 401을 받으면 `refreshCurrentSession()`을 불렀는데, 이 함수도 `currentSessionOrNull()`을 쓰므로 "No refresh token found in current session"을 던졌다. 이 문구가 `UploadManager.friendly()`로 그대로 나갔고 작업은 실패로 끝났다. 7분 뒤 앱을 열었을 때 "결과 없는 녹음 다시 걸기"(DEC-37)로 이어서 끝났다.
4. 처음 추정한 "동시 갱신으로 세션이 지워졌다"는 틀렸다. 세션이 지워졌다면 다시 로그인해야 했는데, 15:14에 같은 세션으로 갱신이 이어졌다.

**고친 내용(D-7, 2026-10-19)**

- `Server.ensureSession()`: 서버 호출 전에 메모리 세션이 없으면 저장된 세션의 refresh token으로 직접 갱신한다. 401을 받으면 강제로 갱신하고 한 번만 다시 부른다. refresh token이 없거나 4xx로 거부되면 `LoginRequired`, 5xx·인터넷 오류는 일시 오류로 다시 시도한다.
- 백그라운드 작업은 시작할 때 `ensureSession()`으로 토큰부터 확보한다(이전에는 `RefreshFailure` 순간에 깨어나면 "로그인이 필요해요"로 멈췄다).
- 사용자 문구: `LoginRequired`는 "로그인이 필요해요. 앱을 열어 다시 로그인해 주세요". 라이브러리 원문은 이 경로로 나가지 않는다.
- 처리가 끝나면(REVIEWABLE) 진행 문구를 "회의록·할 일 후보가 나왔어요"로 덮어쓰므로 이전 오류 문구를 지우는 별도 처리는 필요 없다.
- 남은 것: 앱 화면(`AppRoot`)은 `RefreshFailure`일 때도 로그인 화면을 보여 준다. 잠깐 로그인 화면이 깜빡일 수 있다. 이번 수정 범위에서는 바꾸지 않았다.

분류: 메모 12번 기준 **P1 실사용 품질 개선**(작은 버그 픽스, spec 갱신 불필요). 승인하면 바로 고칠 수 있다.

## 5. 회의 할 일 추출 개선(메모 7번)

### 5.1 실데이터 확인(내용은 저장소에 옮기지 않음)

메모에 적힌 12분 회의(774초)를 운영 DB에서 확인했다.

- 결정 후보 4 · 미결정 2 · 할 일 후보 6.
- 할 일 후보 6개 중 **4개가 결정 또는 미결정과 같은 구간을 근거로 쓴다**(근거 구간 번호가 대부분 겹침). 메모의 "3개 중복"보다 하나 더 많다(미결정 → "~와 논의한다" 형태 1건 포함).
- 사용자는 6개 중 4개를 승인했는데, **승인한 것 중 2개가 결정과 중복된 후보**였다. 즉 기획자에게는 "표기를 ~로 바꾼다" 같은 요구사항 결정이 **곧 본인의 작업**인 경우가 있다.

시사점: v3에서 요구사항형 결정을 할 일에서 빼면 정밀도는 오르지만, 사용자가 실제로 원했던 할 일을 놓칠 수 있다. 그래서 메모 7-2(결정 카드의 "할 일로 만들기")는 **선택이 아니라 v3의 전제 조건**이다. v3만 단독 배포하면 안 된다.

### 5.2 원인 대조

| 메모의 원인 추정 | 확인 |
|---|---|
| 지시문이 할 일을 "앞으로 하기로 한 행동"으로 정의 | 맞음. prompt-v2 원칙 3 "누군가 앞으로 하기로 하거나 맡긴 하나의 행동". 결정과 할 일의 경계 규칙이 없다 |
| 평가 세트가 결정·미결을 점수에 안 넣음 | 맞음. `eval/llm/README.md` "결정 후보·미결정은 참고로 적었고 P0 점수에는 넣지 않는다", `score.mjs`도 actions만 채점 |
| 재현율 우선(87.5% / 98.2%) | 맞음(DEC-28). 경계 사례를 "더 뽑는" 쪽으로 맞춰져 있다 |
| 화자 분리 없음 → 전부 "담당 확인" | 맞음(DEC-27 담당 규칙 A). v3로 해결되지 않는다. 메모 11번 미결정 |

### 5.3 지시문 v3 초안

[`eval/llm/prompt-v3.md`](../../eval/llm/prompt-v3.md)(당시 이름 prompt-v3-draft.md)에 작성했다. **초안이며 처리 함수(`prompt.ts`)에는 넣지 않았다.** v2에서 바뀐 곳:

1. 할 일 정의를 "**약속·요청·배정이 들린 행동**"으로 좁힘(제가 할게요 / ~해 주세요 / ~하기로 해요 / ○○ 님이 ~). 
2. **요구사항·정책 결정**("~로 바꾼다", "~는 넣지 않는다", "~해야 한다")은 decisions에만 둔다. 같은 내용을 actions에 다시 쓰지 않는다.
3. **미결정·확인할 것**은 open_questions에만 둔다. 단, 특정 사람에게 확인을 **맡긴** 경우("○○ 님이 운영팀에 확인해 주세요")는 할 일.
4. 회의 진행 자체의 일("회의록 정리해서 보내기")은 명시적으로 요청·약속이 들릴 때만.
5. 스키마는 이미 decisions → open_questions → actions 순서다(`schema.json`, 스키마 변경 없음). v3는 이 순서를 지시문에 명시해 "결정·미결을 먼저 다 적은 뒤, 거기 없는 약속·요청만 actions에" 쓰게 한다.
6. 담당·기한·보안 규칙은 v2 그대로(DEC-27·31, NFR-08).

기존 정답과의 충돌 점검: dev·holdout 정답 할 일 113개 중 결정·미결과 근거가 겹치는 것은 6개(dev 2 · holdout 4)다. 5개는 "올릴게요", "만들어 드릴게요", "확인할게요", "전화해 볼게요", "주신다고 했어요"처럼 약속·배정이 들려 v3에서도 할 일로 남는다. **H01 "이번 주 안에 개선안 확정하고 바로 현업 리뷰 들어가죠" 1개만 경계 사례**다("~하죠"는 함께 하자는 합의라 v3 규칙 4의 "~하기로 해요"에 해당하는지 모델마다 다르게 볼 수 있음). v3 측정 때 이 항목을 따로 본다. 보류 정답을 보고 지시문을 고치지 않는다는 DEC-28 절차 때문에, 이 경계는 dev 새 케이스(②)로 다룬다.

### 5.4 평가 케이스 추가 계획(DEC-28 절차)

DEC-28 절차: 개선용(dev)만 보고 고치고, 보류(holdout)로 판정, 보안 세트 위반 0, 사용자 승인 후 교체.

## 6. 승인된 회의록 무기한 보관 — 코드·DB 영향

### 6.1 지금 상태(코드·운영 DB 확인)

- 운영 DB의 회의록 10건은 **전부 `draft`**다. **회의록 승인 기능(FR-07 버전 승인)은 아직 구현되지 않았다.** `approval_event.target_type='meeting'` 자리만 있고 승인 함수는 없다.
- 기한이 실제로 집행되는 것은 **음성뿐**이다(`wb-purge-audio`, DEC-35). 전사·회의록 만료 삭제 함수는 아직 없다.
- 따라서 **지금 바꾸면 기존 데이터 이전이 필요 없다.** 정책을 정하기 가장 싼 시점이다.

### 6.2 공통 영향(A·B 어느 쪽이든)

| 위치 | 현재 | 바꿀 것 |
|---|---|---|
| `meeting_version.retention_expires_at` | `timestamptz NOT NULL` (0100) | 마이그레이션: `DROP NOT NULL` 후 **NULL = 무기한**. (대안 `'infinity'`는 NOT NULL을 유지하지만 앱 JSON 파싱(Kotlin `Instant`)이 깨지므로 비권장) |
| `settings.retention_knowledge_years` | `default 1`, `check in (1,2,3)` (0100) | NULL 허용 + 기본 NULL(무기한), 선택지 1/2/3년 유지. 또는 컬럼 의미를 "승인 회의록 보관"으로 이름 그대로 두고 주석만 |
| 회의록 승인 함수(미구현) | Design: "승인 시 지식 수명으로 재계산" | 승인 시 `retention_expires_at = NULL`(설정이 무기한일 때) |
| 처리 함수 `process-record` | 초안은 전사 만료일을 복사 | 변경 없음(초안은 전사 수명 유지, DEC-21) |
| 앞으로 만들 전사·회의록 정리 함수 | 없음 | NULL은 대상에서 제외(`WHERE retention_expires_at < now()`이면 NULL은 자동 제외됨) |
| 설정 화면(S09 RetentionSettings, 앱 미구현) | 1/2/3년 | "무기한(기본)" 추가, 안내 문구 |
| 백업(`wb_backup_export`) | 회의록 포함 | 변경 없음. 백업 크기는 늘지만 회의록 문서는 작다(요약 중심) |
| 삭제(FR-15 3종) | 사용자가 지우면 7일 뒤 삭제 | 변경 없음. 무기한은 "자동으로 지우지 않음"이지 "지울 수 없음"이 아니다 |
| 문서 | DEC-10·DEC-21(지식 1년), 데이터 모델 §4, Design §FR-29 문서 보관, TC-10 | 새 DEC로 개정, TC-10 "승인 회의록은 1년" → "무기한(설정 시 1~3년)" |

### 6.3 근거 링크 처리 — A안 vs B안

현재 근거 구조: `evidence_link.transcript_version_id`(NOT NULL FK) + `segment_ref: {idx: [구간 번호]}`. 근거 **문장 자체는 전사에만 있다.** 회의록 `fields.decisions[].text`는 요약문이라 전사가 지워져도 남는다. 전사가 만료되면 행은 남고 본문(`content`, `segments`)만 비우는 설계라 FK는 깨지지 않는다. **깨지는 것은 "근거 보기"(원문 문장 표시)다.**

| | A안: 승인 시 근거 문장을 함께 저장 | B안: 승인된 기록의 전사는 회의록과 같은 기한 |
|---|---|---|
| DB | `evidence_link`에 `quote text`(또는 `quote_snapshot jsonb`) 추가, 승인 함수가 해당 구간 문장만 복사 | `transcript_version.retention_expires_at`도 `DROP NOT NULL`, 승인 함수가 해당 기록의 전사(원문·교정본 둘 다) 기한을 NULL로 |
| 정리 함수 | 전사 정리는 원래대로 6개월 | 전사 정리가 승인 기록을 건너뜀(NULL이면 자동 제외) |
| 저장량(실측 기반 추정) | 할 일·결정당 1~2문장 ≈ 수백 바이트. 무시 가능 | 실측 전사 ≈ 원문+구간 정보 약 28바이트/초 → 1시간 ≈ 100KB, 교정본까지 ≈ 200KB. 월 30시간 전부 승인 시 연 약 70MB(무료 한도 500MB의 14%/년) |
| 개인정보 | 원문 대부분은 6개월 뒤 사라짐. 인용 문장만 남음 | **원문 전체가 무기한 남음.** "전사 6개월" 안내가 승인 기록에는 거짓이 된다 |
| 기존 규칙과 충돌 | **정면 충돌**: 데이터 모델 §4 "전사에서 복사한 근거 인용은 전사 수명에 따르고 만료 후에는 ID·위치·만료 표시만 남긴다", Design §4.4 "인용으로 전사 만료를 우회하지 않음" | 충돌 작음. DEC-21의 "전사 수명" 예외를 하나 추가 |
| 구현 난이도 | 승인 함수 + 근거 표시 화면이 "전사 있으면 전사, 없으면 저장한 문장" 분기 | 승인 함수 한 줄 + 설정 안내. 근거 표시 화면은 그대로 |
| 사용자가 나중에 원문 전체를 다시 볼 수 있나 | 아니오(인용만) | 예 |

권장: **A안(인용 길이 제한)**. 이유는 (1) 이 메모의 목적이 "회의록을 업무 지식으로 오래 남기기"이지 원문 녹취를 남기기가 아니고, (2) 원문 전체를 무기한 남기는 것은 회사 자료 정책(G5) 측면에서 더 위험하며, (3) 저장량이 작다. 다만 A안은 데이터 모델 §4 원칙을 **사용자 결정으로 개정**해야 하므로, 인용 상한(예: 근거당 2구간·300자)과 "승인한 항목의 근거만"이라는 범위를 함께 정해야 한다. 원문 전체가 필요하다고 판단하면 B안이 구현은 더 쉽다.

사내 문서 보존 규정이 있으면 그 기준이 우선이다(메모 10번).
