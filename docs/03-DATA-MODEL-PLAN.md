# WorkBrain 데이터 모델 계획

버전 0.2 · 2026-10-16 · 개념 모델이며 SQL/컬렉션 상세 스키마가 아님

## 1. 핵심 엔터티와 관계

| 엔터티 | 배치 | 역할·관계 |
|---|---|---|
| User / Settings | P1 | 소유 범위, 시간대, 동의, 보관/예산 설정; 팀 권한은 P5 |
| Project / Area / Resource | P1 | 프로젝트는 지속 영역에 연결, 자료는 여러 프로젝트와 연결 가능 |
| SourceRecord / AudioAsset | P1 | 수집 채널, 실제 발생 시각/불명 여부, 업로드 시각, 파일 해시, 소유자, 보관 만료 |
| SourceProjectLink | P1 | 한 기록과 여러 프로젝트의 연결; 사용자 확인 전 제안 상태 |
| TranscriptVersion | P1 | 원전사/수동 수정 구분, 원본·구간·수정 부모 버전 |
| MeetingVersion | P1 | 원문 근거와 회의록 버전, 초안/사용자 수정/승인 상태 |
| Task | P1 | 프로젝트, 내용, 상태, 우선순위, 미지정 가능한 담당자/기한, 현재 버전 |
| ProjectStateVersion | P1 | 요약·진행 상태, 적용 이력, 근거·변경 이유 |
| AnalysisRun / ProcessingJob | P1 | 입력 버전, 모델/프롬프트, 상태, 재시도, 요청 ID, 사용량 |
| ChangeProposal / ApprovalEvent | P1 | 대상/기준 버전, 변경 전후, 근거, 검토 결과, 중복 실행 키 |
| EvidenceLink / ActivityLog | P1 | 사실·제안과 출처의 관계, 행위자·시각·결과, 원문 대신 ID 중심 로그 |
| CostLedger / BudgetReservation | P1 | 청구 주기, 확정/예상/예약 비용과 만료·실행 상태 |
| DeletionRequest / Tombstone | P1 | 삭제 범위·복구 기한·진행 상태, 백업 복원 후 삭제 재적용 |
| Decision / Requirement / Issue / KnowledgeItem | P2 | 명시적 확정·유효/대체 상태와 프로젝트 연결; P1 후보는 회의록에만 존재 |
| SearchChunk / Embedding | P2/P3 | 원본 버전·소유자·프로젝트·유효성, 원본 삭제/대체 시 동기화 |
| ExternalConnection / AccessAudit | P3 | 읽기 범위, 토큰 만료/철회, 호출 이력 |

기본 관계: SourceRecord 1:N TranscriptVersion 1:N AnalysisRun, AnalysisRun 1:N Proposal, Proposal 1:N EvidenceLink, Proposal 0:1 성공 ApprovalEvent, Project 1:N StateVersion/Task. 기록과 프로젝트는 N:M이다. 재분석은 AnalysisRun을 새로 추가한다.

Archives는 별도 복제 저장소가 아니라 각 프로젝트/자료의 `archivedAt`과 상태다. 보관은 삭제가 아니고, 소유자·원본 ID·이력을 유지한다. 기간 검색에서는 업무 발생 시각과 수집 시각을 구분한다.

## 2. 현재 사실·후보·버전 구분

AI가 생성한 요약/후보는 확인 전까지 확정 프로젝트 상태를 변경하지 않는다. 회의록 승인과 개별 상태 변경 승인은 별개다. 오래된 회의가 늦게 업로드되어도 최신 상태로 자동 승격하지 않는다.

기한은 날짜만/시각 포함/시간대/명확성 상태를 구분한다. '다음 주'처럼 기준이 불명확한 표현은 원문과 확인 필요 상태로 남긴다. 화자 라벨은 실명과 별개다.

모든 출처 링크에는 원본 ID·버전·문장 또는 구간 참조가 있어야 한다. 실제 시간 정렬이 없는 전사에 정확한 초 단위를 만들어 붙이지 않는다. 상태가 대체되면 이전 상태의 유효 종료와 대체 관계를 보존한다.

## 3. 재분석·수동 수정·동시 승인 정책

1. 전사 또는 회의록 수정 시 새 버전을 만든다. 원본 AI 버전을 덮어쓰지 않는다.
2. 재분석 시작 시 입력 전사 버전과 비교 대상 프로젝트/할 일 버전을 고정한다.
3. 동일 버전/분석 설정의 작업 재시도는 같은 실행 키를 재사용한다. 사용자의 명시적 재분석은 새 실행이다.
4. 새 후보는 기존 승인 항목의 원본 연결과 내용 유사성을 비교한다. 동일 근거에서 이미 등록한 항목은 새 할 일 대신 변경 또는 중복 후보로 분류한다. 유사성만으로 자동 병합하지 않는다.
5. 거절한 후보를 같은 입력으로 다시 생성하면 기존 거절 사실을 표시하고 기본 검토 목록에서 중복 숨김한다. 새 근거가 있을 때 재검토 대상으로 표시한다.
6. 승인 직전 대상 버전과 최신 버전을 비교한다. 다른 기기 편집/승인으로 달라지면 충돌 상태로 전환하고 새 차이를 사용자에게 보여준다.
7. 사용자 수정 필드는 잠정적으로 우선 보존한다. 새 AI 값은 제안으로만 표시한다. 되돌리기도 새 변경으로 기록한다.
8. 삭제/만료된 입력에서 실행 중이던 결과가 돌아오면 결과 게시를 거부한다. 승인 시에도 삭제 상태를 재검사한다.

백엔드는 Supabase(PostgreSQL)로 결정되어(DEC-20) 위 보장을 트랜잭션·고유 제약·DB 함수로 구현한다. 실제 동작은 P0에서 시험한다(TC-08).

## 4. 보관과 삭제의 세 가지 의미

기본 보관: 음성 30일, 전사 6개월, 승인된 정리 지식 1년. 30~90일/6~12개월/1~3년 선택을 제공하고 변경에 따른 대상 목록과 비용 영향을 표시한다. 만료 계산은 해당 데이터 최초 저장 시각을 기준으로 하며 단순 편집으로 보관 기한을 무한 연장하지 않는다. 기간 연장은 사용자 명시 설정으로 기록한다.

| 작업 | 즉시 동작 | 남는 데이터 | 복구/최종 삭제 |
|---|---|---|---|
| 원본 보관 만료 | 만료된 음성 또는 전사 본문을 일반 조회·검색·AI 입력에서 제외 | 독립 보관기간이 있는 승인된 회의록/업무 지식, 원본 ID·만료 메타데이터 | 7일 유예 후 대상 본문 삭제; 연장 시 복구 가능 여부 표시 |
| 원본만 삭제 | 사용자가 선택한 음성/전사만 차단, 그 원본만 필요한 대기 작업 취소 | 승인된 파생 자료는 유지한다고 확인 화면에 명시 | 7일 이내 복구, 기한 후 삭제 |
| 연결된 파생 자료까지 삭제 | 원본·초안·검색 조각·직접 파생 자료를 즉시 비노출, 관련 처리 중지 | 복수 출처 항목은 영향 미리보기 후 정화/재검토; 원본을 담지 않는 삭제 감사 메타데이터 | 7일 이내 복구, 이후 삭제 작업 수행 |

복수 출처의 파생 항목은 삭제 원본에 의존하는 문장/필드를 제거하고 재검토 전까지 검색·AI 사용을 막는다. 삭제 영향이 불명확하면 보존을 추정하지 않고 해당 파생 항목을 격리한다. 이미 내보낸 파일·외부 메일·외부 AI 응답은 WorkBrain에서 회수할 수 없음을 삭제 화면에 표시한다.

독립 승인 지식 보관은 장문 원문을 다른 필드에 복사해 전사 만료를 우회하는 방식으로 구현하지 않는다. 전사에서 복사한 근거 인용은 전사 수명에 따르고, 만료 후에는 ID·위치·만료 표시만 남긴다. 요약 지식은 별도 수명의 사용자 승인 데이터임을 고지한다.

## 5. 최종 삭제·백업·복원

- 삭제 시 즉시 소프트 차단. 7일 복구 기간 종료 후 24시간 이내 운영 본문·임베딩·캐시·임시파일 삭제를 목표로 한다. 실패 시 재시도와 미완료 표시를 유지한다.
- 삭제 요청 후 새 백업에는 대상 본문을 포함하지 않는다. 기존 암호화 백업은 생성 후 최대 7일 보관하고 만료시킨다. 백업까지의 최종 소멸은 삭제 시점 기준 최대 8일 목표다. 공급자 자체 보관은 별도 G1 확인 사항이다.
- GCS soft delete/versioning/lifecycle가 애플리케이션 유예기간 뒤에 추가 보관을 만들지 않도록 맞춘다. 실제 소멸 기한이 길면 사용자 표시와 비용을 먼저 수정한다.
- Tombstone에는 불투명 대상 ID·범위·시각만 저장하고 본문·사람 이름을 넣지 않는다. 앱 관리 백업 복원 시 tombstone을 먼저 재적용한 뒤 서비스 접근을 연다.
- DB/메타데이터 백업은 일 1회 암호화 내보내기, 7일 보관, 목표 RPO 24시간/RTO 24시간. 파일 목록·객체 세대·존재 검증을 함께 포함한다. DB만 복원하고 음성까지 복원되었다고 보고하지 않는다.
- 초기 개인 시험 운영에서는 보관기간 내 음성 객체의 서비스 내구성과 7일 복구를 사용한다. 독립된 전체 음성 사본 백업은 포함하지 않으며 공급자 장애 시 복구 한계를 알린다. 독립 사본 요구 시 비용·보관 정책을 별도 개정한다.
- 외부 STT/LLM의 로그·보관·삭제 약관은 앱 삭제와 별개다. G2에서 제공자별 처리 조건을 확인하고 사용자에게 표시한다.

## 6. 접근 제어와 검색

모든 엔터티는 소유자 또는 소유 범위를 추적한다. 연결된 객체의 소유자도 검증한다. 검색 결과뿐 아니라 관련 문서 조회·파일 URL 발급·백업·내보내기·외부 MCP에서 같은 검사를 한다.

P1은 확정 데이터 필터/키워드 검색과 별도 초안 목록이다. P2부터 문서 유효기간·프로젝트·사용자 범위 필터 후 의미 검색을 수행한다. 사용자 입력으로 소유자 필터를 해제할 수 없다. pgvector는 현재 bkend 기본안의 구성 요소가 아니며 G6에서 저장 방식과 비용을 평가한다.
