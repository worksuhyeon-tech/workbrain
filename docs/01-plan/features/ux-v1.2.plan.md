# 실사용 개선 Plan — UX 메모 v1.2

버전 0.1 · 2026-10-19 (Asia/Seoul) · 상태: **Plan 작성, 사용자 검토 전**

근거: [UX 고도화 메모 v1.2](../../WorkBrain-UX-고도화-메모-v1.2.md) · [대조 검토](../../03-analysis/ux-memo-v1.2-review.md) · 결정 DEC-41~46([결정 기록](../../06-RISK-AND-DECISIONS.md))

이 문서는 메모 v1.2를 **언제, 어떤 순서로, 무엇을 바꿔서** 만들지 정한다. 기존 P0~P5 로드맵은 유지하고, 그 사이에 두 갈래를 끼운다.

- **품질 트랙(Q)**: 지금 쓰는 앱의 결함·불편. 기존 P1 작업과 같은 방식으로 바로 진행한다.
- **P1.5 실사용 개선**: P1(MVP)이 끝나고 1주 써 본 뒤 시작하는 새 기능. 메모의 하루 흐름 ②~④(고르기·몰두·끼어들기)를 만든다.

구현은 각 항목의 Design(필요한 것만)과 사용자 승인 뒤에 한다. 이 문서는 구현 완료가 아니다.

---

## 1. 목적과 성공 기준

메모의 핵심 원칙: **떠오르는 생각은 놓치지 않고, 지금 하는 일은 방해받지 않으며, 실행할 일은 사용자가 결정한다.** 보조 원칙: 앱이 만든 항목은 사용자가 고르기 전까지 오늘 화면에 들어가지 않는다.

| 단계 | 성공 기준(실사용 1주 관찰) |
|---|---|
| 품질 트랙 | 처리 중 라이브러리 원문 오류 0건, 회의 1건당 할 일 후보 중 결정·미결 중복 ≤ 1개 |
| P1.5 | 근무일 5일 중 4일 이상 "지금 하는 일"을 골라 시작, 끼어들기 뒤 "돌아갈까요?"에서 복귀한 비율을 기록(목표값은 첫 주 측정 후 정함), 보관함 미처리 수가 주간 리뷰 뒤 줄어듦 |

측정은 앱 활동 기록(ActivityLog)에서 센다. 사용자에게 따로 적게 하지 않는다(메모 12번 "입력 부담을 늘리지 않음").

## 3. 품질 트랙(Q) — 지금 진행

| ID | 항목 | 메모 | 상태 | 서버 변경 | 완료 조건 |
|---|---|---|---|---|---|
| Q1 | "No refresh token" 결함 | 8 | **코드 수정 완료**, 실기기 확인 대기 | 없음 | 백그라운드 처리 중 토큰 갱신 실패가 있어도 오류 문구 없이 이어서 끝남 |
| Q2 | 올리기 시트에서 제목 고치기 | 8 | 대기 | 없음(`source_record.title`) | 올리기 전 고친 제목이 녹음 목록·기록 상세·회의록에 같게 나옴 |

| Q5 | 승인 회의록 3년 + 근거 문장 저장 | 10 | 대기(**회의록 승인 기능 구현 전에** 한다) | 마이그레이션(§6) | 승인 시 기한 = 승인 시각 + 3년, 근거 문장 저장, 전사 만료 뒤에도 근거 보기 됨 |

순서: Q1 확인 → Q2·Q3(화면만, 작음) → Q4 평가 → Q5는 회의록 승인 기능(FR-07) 작업의 첫 단계로 붙인다.

Q4는 v3만 먼저 내보내면 안 된다. 실데이터에서 사용자가 승인한 후보 중 2개가 결정과 겹친 후보였다(검토 §5.1). 기획자에게 요구사항 결정이 곧 본인 일인 경우가 있으므로, 덜 뽑는 대신 결정 카드에서 바로 할 일로 만들 수 있어야 한다.

## 4. P1.5 실사용 개선 — P1 이후

**진입 조건**: P1c MVP 완료(로드맵), P1을 1주 실사용, 그 사이 품질 트랙 Q1~Q4 반영.

메모 12번의 권장 검증 순서를 그대로 단계로 둔다. 각 단계는 끝나면 1주 써 보고 다음으로 간다.

| 단계 | 내용 | 메모 | 하루 흐름 | 선행 | 1주 확인 질문 |
|---|---|---|---|---|---|
| 1.5-A 하나 고르기 | 오늘 탭 최상단 "지금 하는 일" 1개 + 예비 최대 2개, 후보는 기한 임박순 3~5개, "처음 2분 동작" 한 줄(선택), 완료는 취소선으로 남김·"오늘 완료 N건", 못 끝낸 일은 버튼 하나로 내일 후보. **오늘 마감 알림**(DEC-44) | 3 | ② 고르기 | P1 | 실제로 하나를 골라 시작했나? 예비 2개·후보 3~5개가 맞나? |
| 1.5-B 담기·끼어들기 | Quick Capture(DEC-41), 보관함 통합(DEC-42), 끼어들기 [담아두기]/[지금 바꾸기], 멈춤 칸, "멈췄던 ○○로 돌아갈까요?" | 1·2·3 | ① 담기 · ④ 끼어들기 | A | 담아둔 것을 주간에 비웠나? 바꾼 뒤 돌아왔나? |
| 1.5-C 집중 세션 | FR-25a: "이 업무에 집중하기" = 지금 하는 일 확정 + 타이머(25분 기본, 길게 눌러 45·60분), 종료 시 계속/쉬기, 체크포인트(선택) | 4 | ③ 몰두 | A | 타이머가 방해가 되지 않았나? 체크포인트를 남겼나? |
| 1.5-D 업무 재개 카드 | 마지막으로 연 항목·마지막 세션 자동 기억, 사용자 메모 우선, AI 추론은 "추정" 표시 | 5 | ④ 복귀 | C | 다시 열었을 때 바로 이어서 했나? |

1.5-B의 보관함 통합은 화면 이름 변경이 아니다. 검토함(S06)·기록 상세 바로 추가(DEC-23)·변경 제안(DEC-38)의 동작을 유지한 채 아이디어를 함께 보여 주는 것이다(§6 주의).

**P1.5에 넣지 않는 것**(1.5-D 이후 실사용 결과를 보고 P2 배치를 다시 정한다):

| 항목 | 메모 | 이유 |
|---|---|---|
| PARA 주간 점검 화면·개입 필요 점·트리+지도맵 | 6 | 점 기준·지도맵 형태가 미결(메모 11번). 집중 세션·체크포인트 데이터가 있어야 "개입 필요"를 정할 수 있다 |
| KPI 1단계·AI 주간 리뷰 | 9 | 1.5-C 집중 세션 데이터가 2주 이상 쌓여야 의미가 있다. FR-20(P2 브리핑)과 묶는 것이 자연스럽다 |
| FR-25b 매트릭스·습관·통계 | 4·9 | P4 그대로(DEC-43) |

## 5. 지시문 v3 평가(Q4, DEC-46)

DEC-28 절차(개선용만 보고 고침 → 보류로 판정 → 보안 세트 위반 0 → 사용자 승인 후 교체)를 그대로 따른다. 실제 회의 원문은 넣지 않고 보험 보상 가상 업무·가상 인물로 만든다.

| 순서 | 내용 | 산출물 |
|---|---|---|
| 1 | 정답 규칙 개정: 결정·미결과 같은 내용을 할 일로 뽑으면 "결정 중복" 오답. 결정·미결도 채점 | `eval/llm/README.md` |
| 2 | 요구사항 정리형 가상 회의 6건(dev D13~D15, holdout H13~H15). 건마다 결정 4~6, 미결 1~3, 진짜 약속·요청 2~4, "결정이지만 특정인에게 맡김" 1개 이상 | `dev.json`·`holdout.json` |
| 2-1 | **실사용 회의 1건(2026-10-19, 개발자와 12분)을 holdout에 추가**(사용자 결정). 전사·정답은 git 제외 폴더 `data-private/eval/`에만 두고 공개 저장소에는 결과 수치만 적는다. 정답(진짜 할 일)은 초안을 만들어 사용자가 확인. 주의: 이 회의는 대조 검토 §5.1에서 이미 살펴봤으므로 v3 초안 작성에 간접 영향이 있었을 수 있다 | `data-private/eval/real-holdout.json`, `score.mjs` 경로 옵션 |
| 3 | 채점기: 짝 없는 추출 중 정답 결정·미결 구간과 겹치고 제목이 비슷한 것을 "결정 중복"으로 따로 셈 | `score.mjs` |
| 4 | v2 기준선 재측정(기존 수치는 결정 중복을 안 셌음) | `runs/` |
| 5 | v3: dev로만 조정 → holdout 1회 → 보안 10건 | `runs/` |
| 6 | 판정: holdout 정밀도 ≥ 90%, 재현율 ≥ 85%, 결정 중복 ≤ v2의 1/3, 허구·출처 누락·보안 위반 0 | 결과 보고 → 사용자 승인 → 새 DEC |
| 7 | 반영: 결정 카드 "할 일로 만들기"와 함께 처리 함수 v11 | 앱·Edge Function |

비용: gpt-6-luna 기준 dev+holdout+보안 1회에 수십 원. 경계 사례 H01("~하죠")은 보류 정답이라 보고 고치지 않고, dev 새 케이스로 다룬다.

## 6. 데이터 확장 포인트

메모 12번 "향후 연동에 필요한 데이터 관계"를 단계별로 모았다. 이름은 가칭이며 Design에서 확정한다.

| 단계 | 대상 | 바꿀 것 | 이유·주의 |
|---|---|---|---|
| Q5 | `meeting_version.retention_expires_at` | 스키마 그대로(NOT NULL 유지). 승인 함수가 승인 시각 + 설정 연수로 다시 계산 | 무기한이 아니므로 NULL·`'infinity'`가 필요 없다 |
| Q5 | `settings.retention_knowledge_years` | 기본값 1 → 3, 선택지 1/2/3 그대로 | 이미 만든 설정 행의 값도 3으로 바꿀지는 마이그레이션 때 확인(사용자가 직접 고른 값이 아니면 3) |
| Q5 | `evidence_link` | `quote text` 추가(근거당 2구간·300자). 승인 함수가 승인 항목의 근거 구간만 복사 | 근거 보기는 "전사 있으면 전사, 없으면 저장한 문장". 승인 전 후보·초안에는 복사하지 않는다 |
| Q4 | 할 일 직접 생성 | 결정 카드에서 사용자가 만든 할 일은 AI 후보 승인 경로가 아니라 수동 생성(FR-08) + 출처로 그 결정 연결 | AI 제안 규칙(분석 실행·승인 기록)을 거치지 않는다 |
| 1.5-A | `today_pick`(가칭) | 날짜·할 일·칸(now/spare/paused)·처음 2분 동작·멈춤 메모·순서 | **할 일 상태(open/doing/done)에 '멈춤'을 넣지 않는다.** 멈춤은 오늘 고르기의 칸이지 할 일의 상태가 아니다. 다른 화면·기기 동기화 규칙을 건드리지 않기 위함 |
| 1.5-A | `task.done_at` | 완료 시각 추가 | "오늘 완료 N건", 이후 KPI의 기준. 완료 취소 시 NULL |
| 1.5-A | 알림 | 기기 로컬 알림(오늘 마감만), 서버 푸시 없음 | 알림 권한 거부 시 앱 안 표시만 |
| 1.5-B | `inbox_item`(가칭) | 본문·추정 맥락(프로젝트·화면, "추정" 표시)·상태(kept/archived/converted)·만든 시각·전환 대상 | **AI 제안(`change_proposal`)과 같은 표에 넣지 않는다.** 사용자 메모에는 분석 실행·근거·승인 기록 규칙이 필요 없다. 화면에서만 한 목록으로 합친다 |
| 1.5-B | `change_proposal` | "계속 보관" = `snoozed_until` NULL 허용 + 보관 표시 | 보관 중에도 근거 전사 만료는 진행(DEC-15) → 보관함에 만료 예정일 표시 |
| 1.5-C | `focus_session`(가칭) | 할 일·프로젝트·시작·끝·설정 분·실제 집중 초·끝난 방식(계속/쉬기/중단) | 집중 시간과 진척률을 섞지 않는다(메모 4번) |
| 1.5-C | `checkpoint`(가칭) | 세션·마지막 완료·다음 행동·중단 이유(모두 선택) | 1.5-D 재개 카드와 KPI 중단 사유의 원천 |
| 1.5-D | 마지막 연 항목 | 기존 ActivityLog 재사용(새 표 없이) | 사용자 메모 > 체크포인트 > 확정 할 일·회의록 > AI 추정 순으로 보여 줌 |

모든 새 표는 `workspace_id`·소유자 RLS·백업 대상·삭제 3종(FR-15) 규칙을 기존 표와 같게 따른다.
